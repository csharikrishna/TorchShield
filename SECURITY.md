# Security Policy and Cryptographic Architecture

**Current Release Status:** AHCC Secure AI Checkpoint Platform v0.7.0 (Restricted Pilot Approved).  
**Vetted Cryptographic Baseline:** NIST SP 800-38D AES-256-GCM + RFC 5869 HKDF-SHA256 + RFC 8032 Ed25519.  
**Custom AHCC Transform:** Strictly Experimental and Insecure for Production.  

---

## 1. Executive Security Architecture

The AHCC GPU Engine project has pivoted to a dual-tier architecture:

1. **Production Checkpoint & Tensor Security Engine (`ahcc.checkpoint` & `ahcc.secure`):**
   - Built on vetted, hardware-accelerated **AES-256-GCM** authenticated encryption (via `cryptography`/OpenSSL).
   - End-to-end authenticated chunked streaming for PyTorch model weights and state dictionaries.
   - Per-artifact subkey derivation using **HKDF-SHA256** (RFC 5869) with a 32-byte public derivation salt and domain separation.
   - Strictly enforced deterministic chunk nonces under NIST SP 800-38D, guaranteeing strictly zero nonce collisions ($P=0$) under a given key, with cross-checkpoint independence bounded by the $2^{-128}$ birthday bound.
   - Authenticated manifests cryptographically binding file identity, layer names, chunk sequences, shapes, and dtypes.
   - Atomic writes (`.tmp` staging $\to$ `fsync` $\to$ `replace`) preventing corrupt state during crashes or disk failures.
   - Fail-closed parsing rejecting pickle/untrusted deserialization, memory-exhaustion payloads, and tampered chunks.

2. **Archived Research Prototype (`archives/v1_chaotic_crypto_prototype/`):**
   - The initial research blueprint attempting chaotic map encryption has been safely archived.
   - **It is NOT part of the production package.** The production checkpoint pipeline uses exclusively vetted AEAD cryptography.

## 2. Threat Model & Explicit Trust Boundaries

Cryptographic encryption protects against unauthorized inspection, weight tampering, supply-chain deserialization exploits, and out-of-order execution:

| Security Vector | Platform Guarantee | Mechanism | Notes & Boundaries |
| :--- | :---: | :--- | :--- |
| **Ciphertext Confidentiality** | **YES** | AES-256-GCM / ChaCha20-Poly1305 | Protects weights and training state at rest and in transit. |
| **Ciphertext Tampering / Integrity** | **YES** | GCM 128-bit Auth Tag + AAD | Modifying any bit fails closed with `CheckpointError`. |
| **Chunk Reordering / Splicing** | **YES** | Manifest Digest + Chunk Index AAD | Chunks from other files or swapped within a model are rejected. |
| **Metadata / Header Tampering** | **YES** | Authenticated Manifest AAD | Altered layer names, dtypes, or shapes fail authentication. |
| **Arbitrary Code Execution (Pickle)** | **YES** | Restricted Binary Tensor Format | Zero pickle usage; impervious to deserialization exploits. |
| **Resource Exhaustion / OOM Bombs** | **YES** | Defensive Header Limits | Max dimensions, tensor counts, and byte budgets validated before allocation. |
| **Model Publisher Authenticity** | **YES** | Ed25519 Digital Signatures | Publisher signs canonical manifest; transitively signs all tensor chunks. |
| **Replay / Rollback Attacks** | **YES** | Freshness Ledger | Monotonic generation counters prevent replay of superseded checkpoints. *Boundary: Local ledgers cannot detect VM/hypervisor snapshot reverts.* |
| **Host Memory / GPU VRAM Extraction** | **NO** | Documented Limitation | Once decrypted into host RAM or GPU VRAM, tensors are subject to OS/process memory inspection. |
| **Malicious Pre-Encryption Weights** | **NO** | Documented Limitation | If a model was backdoored before encryption, authenticated encryption faithfully preserves the backdoored weights. |
| **Physical Side-Channel Attacks** | **NO** | Documented Limitation | PyTorch operations and host memory transfers are not hardened against physical side-channel or fault-injection attacks. |

## 3. Key Management and Nonce Uniqueness Policy

### 3.1 Key Lifecycle & Derivation
- **Secret Input Keying Material (IKM):** Master keys and Data Encryption Keys (DEKs) must be 256-bit (32 bytes) uniformly random values generated by CSPRNG (`AESGCMEnvelope.generate_key()` or `secrets.token_bytes(32)`) or via cloud HSMs (`AWSKMSProvider.generate_data_key()`). IKM is strictly secret and resides only in volatile memory during process execution.
- Keys must never be hard-coded, checked into source repositories, or logged in exceptions.
- Key identifiers (`key_id`) are non-secret identifiers and remain separate from secret key bytes.
- **Public Derivation Salt:** When encrypting checkpoints, a fresh 32-byte cryptographic random salt is generated and written in plaintext at bytes `0x09 - 0x28` of the container header. Under RFC 5869, this salt is a **public extraction parameter**, NOT secret keying material. Salt secrecy is not required for HKDF-SHA256 security proofs.
- **Domain-Separated Subkey Derivation (Version 5):** The system extracts a Pseudorandom Key (PRK) and derives independent, domain-separated subkeys:
  $$\text{PRK} = \text{HKDF-Extract}(\text{salt}=\text{public\_salt}_{32\text{B}}, \text{IKM}=\text{DEK}_{32\text{B}})$$
  $$\text{manifest\_key} = \text{HKDF-Expand}(\text{PRK}, \text{info}=b"\text{AHCC-v5-Manifest-Key::"} + \text{artifact\_id}, L=32)$$
  $$\text{chunk\_key} = \text{HKDF-Expand}(\text{PRK}, \text{info}=b"\text{AHCC-v5-Chunk-Key::"} + \text{artifact\_id}, L=32)$$

### 3.2 Nonce Construction & Collision Bounds (NIST SP 800-38D Compliance)
To prevent AES-GCM nonce reuse under any circumstances:
- Nonces are 96 bits (12 bytes).
- **Manifest Nonce:** Fixed 96-bit domain-separated constant $b"\text{MANI}\backslash\text{x00}\backslash\text{x00}\backslash\text{x00}\backslash\text{x00}\backslash\text{x00}\backslash\text{x00}\backslash\text{x00}\backslash\text{x00}"$. Used exactly once under `manifest_key`.
- **Chunk Nonces:** Monotonic counter construction combining a 32-bit domain prefix and a 64-bit big-endian counter:
  $$\text{nonce}(seq) = b"\text{CHNK}" + \text{struct.pack}(>Q, seq), \quad 0 \le seq < \min(\text{total\_chunks}, 2^{64}-1)$$
- **Intra-Key Guarantee ($P=0$):** Under a single `chunk_key`, `_ChunkCryptoSession` enforces strictly monotonic sequencing and seals upon completion. Under NIST SP 800-38D §8.2.1, the probability of a nonce collision under that key is identically zero ($P(\text{collision} \mid K_{\text{chunk}}) = 0$).
- **Cross-Key Guarantee (Birthday Bound $2^{-128}$):** Across independent checkpoints, collision avoidance relies on independent 256-bit random keys and public salts. Two independently generated 256-bit keys have an infinitesimal collision probability bounded by the birthday paradox ($2^{-128}$). The combined protocol guarantees that the same $(Key, Nonce)$ pair is never reused.

## 4. Reassessment of the Experimental AHCC Cipher

A detailed cryptanalytic review (`reports/PHASE2_CIPHER_REASSESSMENT.md`) established:
1. **Univariate vs. Multivariate Correction:** The Phase 1 claim that an algebraic degree of $3^4 = 81$ permits recovering the cipher in $<100$ known pairs was mathematically flawed. In $N=64$ dimensions, dense Cauchy mixing produces up to $1.25 \times 10^{41}$ multivariate monomials, making simple interpolation impossible.
2. **Fatal Inherent Weaknesses:** Despite the correction above, AHCC has critical vulnerabilities:
   - **Legacy Seed Entropy Collapse:** Key schedule collapses seed into a single 32-bit state modulo $p-3$ ($\le 2^{32}$ security, exhaustible in $<2$ seconds on GPU).
   - **Algebraic Invertibility:** Key schedule recurrence is step-by-step invertible in $O(1)$ operations using Tonelli-Shanks modular square roots.
   - **Zero Authentication:** Direct AHCC encryption has no MAC or integrity verification; bit flips corrupt plaintexts silently.
   - **Deterministic ECB Behavior:** Without IVs, identical blocks leak exact equality.
   - **Dense Cauchy Bottleneck:** $O(N^2)$ scalar multiplications over $\mathbb{F}_p$ cannot leverage GPU Tensor Cores, resulting in slow throughput ($\sim 11-80\text{ MiB/s}$ vs $>2,000\text{ MiB/s}$ for CPU AES-GCM).

**Policy:** The raw AHCC cipher must remain strictly a research prototype.

## 5. Security Vulnerability Reporting

If you identify a security defect, timing vulnerability, or envelope flaw in the production checkpoint implementation:
1. Do not file public GitHub issues.
2. Contact the security maintainers with a reproducible proof of concept.
3. Include environment details, hardware specifications, and attack traces.
